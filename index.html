2025 — now · Agora · full-time

Governance rails for Optimism, ENS & Uniswap

Full-stack engineer on Agora's multi-tenant governance platform: proposal creation and voting, delegate discovery, grants, retro funding, attestations and rewards — the infrastructure DAOs run on.

  • Safe multisig, first-class. Automatic Safe detection, live signer tracking across offchain SIWE and onchain transactions, cross-device continuity. Read the write-up
  • Notifications Hub. Wallet-linked, per-event controls across email, Discord, Slack, Telegram and browser push — verification, retries, deduplication, delivery analytics. Read the write-up
  • Governance data. EAS-backed attestations and eligibility, indexed onchain voting data, reward distribution.
Read the case study

Problem

Optimism, ENS, and Uniswap needed one governance platform covering proposals, voting, delegation, grants, and identity — for very different DAOs, with wallet UX spanning EOAs, Safe multisigs, and users who have never held a wallet.

Ownership

Architecture and end-to-end delivery of multi-tenant governance features: Safe-native signing, the Notifications Hub, authentication, attestation-backed eligibility, and citizenship registration.

Constraints

One codebase serving all tenants behind per-tenant flags; live DAOs that cannot break mid-vote; every change backward-compatible; security stakes measured in treasuries.

Architecture

A multi-tenant Next.js application over indexed onchain governance data; reusable SIWE JWT authentication; Safe-aware signing flows with live signer tracking; a five-channel notification platform with verification, retries, and deduplication.

Hard decisions

Replacing per-action client signatures with server-owned SIWE JWT authorization; introducing embedded wallets without touching the relayer paths existing tenants depend on; sizing relay gas from estimates instead of fixed limits after tracing out-of-gas reverts in production.

Outcome

Shipped across a dozen-plus tenant DAOs. 90 merged PRs in the public repositories; two public product write-ups.

2025 · TakeAIt

A ticketing platform where coding agents are users

Built at Agora: Claude Code and Codex agents claim tickets, spin up isolated workspaces on private GCP VMs, execute, stream state, open pull requests — and pause when they need a human.

  • Zero-inbound security. Poll-only runners, rotating hashed keys, per-secret IAM, per-agent Unix users, controlled egress.
  • Crash-resilient execution. Atomic work claiming, journal/replay recovery, ticket-status reconciliation, redacted logs.
  • Human-in-the-loop. Comment-driven pause and redirection, mention-to-wake conversations, supervision from the web UI and a Go CLI.
Read the case study

Problem

Coding agents are productive but ungoverned: pointed at production repositories they need isolation, auditability, and human control — or they are a liability instead of leverage.

Ownership

The platform end to end: Next.js/PostgreSQL control plane, GCP provisioning layer, and the multi-daemon Go runner runtime.

Constraints

No inbound network path to runners; secrets never at rest on execution hosts; agents crash mid-run and must recover without duplicating work; humans must be able to redirect a run in flight.

Architecture

Poll-only Go runners with rotating hashed keys and per-agent Unix users; credentials in GCP Secret Manager with per-secret IAM and temporary materialization; atomic verb-based work claiming; a journal/replay model for crash recovery; SSE state streaming and automated pull-request creation.

Hard decisions

Zero-inbound polling over push (larger latency budget, radically smaller attack surface); verb-based atomic claiming so concurrent agents never double-claim; journaled replay over stateless retries so partial work survives a crash.

Outcome

Claude Code and Codex agents ship reviewed pull requests daily on Agora's internal engineering — and the same workflow is how I build my own software.

Games that live on mainnets and stay up

  • Sekai Glory 2024–2025 · part-time lead Led full-stack delivery of a trading-card game: 16 upgradeable contracts, real-time PvP matchmaking rebuilt around atomic match creation and Redis-persisted queue state, five languages — migrated live from Blast to Ronin.

  • Realm 2023–2024 · part-time Fully onchain strategy ecosystem: a Solidity monorepo spanning 55 game domains with 176 contracts live on Arbitrum One, three subgraphs serving live state, an AWS rewards engine distributing weekly ARB.
Read the case study

Problem

Onchain games fail in ways web apps don't: chains get abandoned mid-product, NFT state is too slow for real-time gameplay, and randomness with money attached invites manipulation.

Ownership

Led full-stack delivery at Sekai Glory; DAO council and lead engineering at Lifeverse; full-stack and contracts at Realm — application, contracts, indexers, and infrastructure in each.

Constraints

Live players during the Blast-to-Ronin migration; matchmaking that cannot strand a queue; provable fairness for reveals and rewards; small teams owning everything.

Architecture

Hybrid state: NFTs mirrored into PostgreSQL for low-latency simulation with idempotent, recoverable mint and upgrade flows. 16 UUPS-upgradeable contracts with 20 Forge test suites (Sekai). Deterministic battle simulation with commit-reveal randomness (Lifeverse). A 55-domain Solidity monorepo with three subgraphs indexing 116 contracts (Realm).

Hard decisions

Mirroring chain state instead of reading it live — accepting reconciliation complexity to get game-grade latency; rebuilding matchmaking around atomic match creation and Redis-persisted XState after stuck-queue failures; migrating contracts, indexer, and app to Ronin without rebuilding the product.

Outcome

176 contracts live on Arbitrum One; the Sekai migration shipped with the game still running; the stuck-queue failure mode was eliminated rather than mitigated.
